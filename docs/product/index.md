# Продуктовое описание `jwt`

## Какую задачу решает

Сервис получает запрос и должен ответить на вопрос «кто это». Классический ответ - идентификатор сессии в куке и таблица
сессий в базе: тогда каждый запрос упирается в чтение из общего хранилища, а несколько сервисов вынуждены делить одну
базу или ходить в сервис авторизации по сети.

JWT переворачивает схему: утверждения о пользователе едут в самом токене, а подпись позволяет получателю проверить
их подлинность локально. Ни базы, ни сетевого вызова: только общий секрет и арифметика.

Библиотека закрывает обе стороны обмена:

- **Выпуск токена** с типовыми утверждениями (`sub`, `iss`, `aud`, `exp`, `nbf`, `iat`, `jti`) и своими полями.
- **Проверку** подписи и утверждений, где ожидания задаёт проверяющая сторона, а причина отказа возвращается
  машиночитаемым кодом.
- **Проверку чужих токенов** на `RS256`: подпись проверяет внешний объект, утверждения - библиотека, а результат
  и коды отказа те же, что при симметричной проверке.
- **Диагностический разбор** без проверки подписи - для чтения `kid` перед выбором ключа.

Типовые применения: авторизация в HTTP-API, межсервисные вызовы, ссылки с ограниченным сроком действия, одноразовые
приглашения и подтверждения почты.

## Чем отличается от альтернатив

| Вариант | Проверка | Отзыв | Замечания |
|---|---|---|---|
| **jwt (HMAC)** | Локальная, без сети | По истечении `exp` | Общий секрет знают и выпускающая, и проверяющая сторона |
| Сессия в базе | Чтение из хранилища | Мгновенный | Общая база или сервис сессий на каждый запрос |
| JWT на RSA | По открытому ключу издателя | По истечении `exp` | Проверяющему не нужен секрет; подпись проверяет `jwt-verify`, утверждения - эта библиотека |
| Самодельная подпись | Локальная | Своя | Формат несовместим ни с чем; ошибки в сравнении подписей типичны |
| Basic-аутентификация | Локальная | Смена пароля | Секрет уезжает в каждом запросе, утверждений нет |

Главное практическое отличие от самодельного формата - совместимость. Токен, выпущенный этой библиотекой, проверяется
любым другим клиентом JWT, и наоборот; отладка идёт через привычные инструменты вроде jwt.io.

Отличие от сессии в базе - цена проверки. За неё платят невозможностью мгновенного отзыва: выданный токен действует
до `exp`. Отсюда практика коротких сроков жизни и обновляющих токенов, которые хранятся уже на стороне сервера.

## На какую спецификацию опирается

- [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519) - JSON Web Token: состав утверждений, `NumericDate`, правила `aud`.
- [RFC 7515](https://www.rfc-editor.org/rfc/rfc7515) - JSON Web Signature: компактная сериализация, `base64url`
  без выравнивания (приложение C), требование понимать заголовок `crit`.
- [RFC 7518](https://www.rfc-editor.org/rfc/rfc7518) - алгоритмы: семейство HMAC (`HS256`, `HS384`, `HS512`).
- [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104) - собственно HMAC, собранный поверх `ХешированиеДанных`.

Соответствие проверено на эталонных значениях:

- HMAC совпадает с тестовыми векторами [RFC 4231](https://www.rfc-editor.org/rfc/rfc4231) для SHA-256, SHA-384 и SHA-512,
  включая случай ключа длиннее блока.
- Подписанный токен байт в байт совпадает с эталоном jwt.io для `HS256`.
- Токен из [RFC 7515, приложение A.1](https://www.rfc-editor.org/rfc/rfc7515#appendix-A.1) успешно проверяется.
- `aud` принимается и строкой, и массивом строк (RFC 7519, раздел 4.1.3).

## Безопасность

Реализованы защиты, отсутствие которых регулярно приводит к обходу авторизации в других библиотеках:

- **Алгоритм `none` запрещён всегда**, даже если он указан в списке разрешённых.
- **Список алгоритмов задаёт проверяющая сторона.** Значению `alg` из самого токена не доверяем, поэтому подмена
  алгоритма не проходит.
- **Подписи сравниваются за постоянное время**: по длительности проверки нельзя подобрать корректную подпись.
- **Заголовок `crit` отвергается**: RFC 7515 требует понимать критические расширения, а библиотека их не поддерживает.
- **Нагрузка невалидного токена не возвращается**, поэтому её нельзя случайно использовать.
- **Пустой секрет отвергается** на этапе подписи.

## Ограничения

- **Выпуск - только HMAC.** Подписать `RS256` или `ES256` библиотека не может: для этого нужен закрытый ключ
  и полноценная реализация RSA или эллиптических кривых. Попытка подписать таким алгоритмом вызывает исключение,
  а не молчаливый откат на HMAC.
- **Секрет знают обе стороны.** При HMAC проверяющий может и выпускать токены. Если этого допускать нельзя,
  нужна асимметричная схема: чужие токены на `RS256` проверяются функцией `ПроверитьАсимметричный` в паре
  с пакетом [jwt-verify](https://github.com/oscript-library/jwt-verify), который добывает открытые ключи
  издателя из JWKS и проверяет подпись.
- **Отзыв не предусмотрен.** Выданный токен действует до `exp`. Списки отзыва, идентификаторы `jti` в чёрном списке
  и обновляющие токены реализует вышестоящий код.
- **Содержимое токена не зашифровано.** Нагрузка кодируется base64url и читается любым желающим; JWE не поддерживается.
  Персональные данные и секреты в утверждения класть нельзя.
- **Проверка `typ` необязательна по умолчанию.** Если сервис выпускает несколько видов токенов, ожидаемый `typ`
  или своё утверждение нужно задавать явно.
- **Точность времени - секунда**, как требует `NumericDate`. Расхождение часов между узлами компенсируется параметром
  `Допуск`.
- **Разбор без проверки подписи доступен**: метод `Разобрать` существует ради `kid` и диагностики, и его результату
  доверять нельзя.
